- `skills pin name@version` no longer requires `--remote`: an exact version only exists on an instance, so the remote fetch is implied for `name@version` pins (the flag stays accepted; the no-instance refusal now says so instead of "needs a configured Skills instance") (hasna/apps#1671).
- `skills push` refuses a skill that declares no version anywhere (skill.json, SKILL.md frontmatter, package.json) instead of silently publishing an invented `0.1.0`; `--version <v>` is the escape hatch, and the refusal applies to `--dry-run` too.
- `skills push` distinguishes an idempotent publish from a fresh one: a push whose `name@version` already exists with the same digest (including a second `--force-new-version` from the same sources, whose bump lands on an already-published version) is reported as "already published as X — no new version created" instead of "published as X". The publish response now carries `alreadyPublished: true` for the idempotent case.
- The version manifest's `provenance.gitRemote` strips userinfo before recording: a remote configured with embedded credentials (`https://user:token@host/...`) never leaks them into `manifest.json` in the bucket; scp-style `git@host:path` remotes pass through unchanged.
- The purged-slug guard in `skills pull` now accepts either proof that a local install came from the instance: the recorded revision id or the recorded content digest of an exact-version install — so a digest-marked `name@version` install is reported `purged` instead of silently swapped for the bundled skill of the same name.
- Version-object retention is documented on the bucket write path (lifecycle-expire `<prefix>/skills/<org>/<slug>/<version>/` objects per policy; never lifecycle-expire the content-addressed `<prefix>/bundles/` namespace, which versions share); operating the rule stays an infra follow-up.
