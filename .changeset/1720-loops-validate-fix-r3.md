`loops-mcp` fails closed at startup, in every mode (hasna/apps#1720 validation, round 3; owner ruling 2026-09-07). On 0.7.0 the MCP entry selected its transport without ever resolving the client connection: with no credential resolvable (empty `HASNA_HOME`, absent Keychain account, no env key) the default Streamable HTTP mode printed `Streamable HTTP listening on http://127.0.0.1:8890/mcp` and answered `initialize` (HTTP 200, serverInfo open-loops), and `--stdio` answered `initialize` then exited 0 on EOF — only the tool calls failed, per request. The new startup gate (`src/mcp/startup-gate.ts`) runs the same `resolveCloudStorage` chain every tool uses per call ONCE, before any listener is bound or any transport is connected: with no connection configured the process exits 1 with the CLI's `no loops client connection is configured` refusal as the first stderr line (naming `HASNA_LOOPS_API_KEY`, the Keychain item `hasna.credentials.loops.api-key`, the `~/.hasna/loops/config/credentials` file and the `HASNA_LOOPS_CONNECTION=file` opt-in — never a value), `initialize` is never answered, no port is bound, and nothing is created under the app home. A deliberate tier that cannot be honoured is refused the same way rather than resolved around: `HASNA_PROFILE` naming a missing profile file, an unsafe (not owner-only) credentials file, the retired `HASNA_LOOPS_CONNECTION=api` selector, and a `HASNA_LOOPS_API_KEY_REF` vault pointer, which the chain accepts on shape alone and the gate now dereferences once exactly as the transport does per request. The explicit `HASNA_LOOPS_CONNECTION=file` opt-in still serves and announces "local mode" once on stderr; `--help`, `--version` and `list-tools` still answer ahead of the gate; every tool still re-resolves per call. Hermetic tests cover the gate in-process (fake home, injected Keychain runner, injected vault completer) and as a spawned `loops-mcp` in both transports (initialize NOT answered, no listener, no `*.db`).
