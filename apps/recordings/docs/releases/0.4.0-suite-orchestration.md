# Recordings release suite orchestration

The release gate keeps the dynamic `ci-linux-suite.ts` gated-file manifest. On
Darwin it runs three sequential groups, with no allowed failures:

| Group | Selection | Process boundary |
| --- | --- | --- |
| Publication | Finalized installer and output-publication describes | `helpers/run-publication-fixtures.py` supervises one OS sandbox; its capability probes must pass before tests start. |
| Lifecycle | Every other test in `macos-app-lifecycle.test.ts` | Direct Bun runner; signing fixtures apply their own child sandboxes. |
| Ordinary | Every other manifest-gated file, without a name filter | Direct Bun runner; identity, trigger, signing and other host-tool fixtures apply their own audited child boundaries. |

The publication and lifecycle name patterns are complementary. Publication
receipts include the registration inventory of the shared lifecycle file, so the
gate can compare both inventories and require exactly one selected owner per test
instance. Duplicate parameterized names remain separate instances. A new describe
in the publication-only file that the selected pattern does not own fails coverage
and requires an explicit partition update. New ordinary files enter automatically
through the existing manifest discovery. Non-Darwin platforms retain one unfiltered
Bun group over the entire gated manifest.

Every group must exit zero without a signal or process error and provide a complete,
nonempty JUnit report plus a matching Bun completion summary. The strict parser
checks file membership, XML balance, totals, selected pass/skip counts, and skipped
status for tests assigned to the other group. Bun 1.3.14 reports name-filtered tests
as skipped in JUnit even though they are absent from its console count; these are
excluded from the aggregate, while actual platform skips remain reported. A silent
`process.exit(0)`, missing group, stale report, extra file, truncated XML, unaccounted
failure, duplicate selection, or missing selected file cannot pass.

Each launch receives a new temporary home/cache and a clean environment without
inherited credentials, service selectors or runtime injection variables. Its owned
`bin/bun` symlink pins shell children to the gate's exact executable. This does not
replace Darwin OS confinement: changing HOME cannot isolate native defaults,
Keychain or TCC. No gate environment or bin is installed globally.

The publication supervisor exports only its fixed, bounded, no-follow regular-file
JUnit receipt to a new file in the gate's owned canonical 0700 report directory.
The sandbox itself cannot write outside its fixture root. The gate never wraps this
supervisor or self-confined fixtures in another sandbox, because Darwin rejects
nested `sandbox_apply`. Bun child runners use `--no-orphans`; the publication
supervisor retains its existing bounded process-group cleanup. Gate group deadlines
are 6 minutes for publication and 30 minutes for each other group, in addition to
per-test bounds. Logs and XML are preserved per group, with a combined `suite.log`.

`bun scripts/release-suite-gate.ts --plan` validates and prints the complete plan
without executing tests. `prepublishOnly` continues to require typechecking before
the gate; no failing-test allowlist or quarantine exemption was added.

## Focused validation

Bun 1.3.14 on Darwin:

- Orchestration, existing manifest partition, and prepublish wiring regressions:
  **40 pass, 0 fail, 81 assertions** across 3 files. Real toy Bun subprocesses prove
  complementary JUnit accounting and refusal of early exit zero; they never invoke
  the actual broad gate.
- Confined publication report export: **42 pass, 93 existing skips, 0 fail,
  287 assertions**, 82.60 seconds. The real report parsed and reconciled against
  the console; its shared signing registrations correctly require the separate
  lifecycle group before aggregate coverage can pass.
- Strict TypeScript check for the gate and new test file passed; Python syntax
  validation passed. Read-only `--plan` retained the manifest file set.
- Required affected build was attempted but failed in unrelated sparse-worktree
  dependencies for Bridge/Servers (`commander`, `zod`, `@hasna/events/commander`).
  Required root check passed names and dependency direction, then failed because
  the Contracts manifest validator could not resolve its `commander` dependency.

The broad gate has deliberately not run in this task: remaining CLI, status,
maintenance and Tailscale fixture audits are owned by the native fixture lane, and
its recorder audit must remove the existing test that can call a real installed
`rec` process. Signing changes also need integration before their group can run.
This document records orchestration evidence, not a completed release acceptance.
