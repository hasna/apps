# Upstream credential-startup fixture confinement

The credential-startup changes merged at `14f055ef5` exposed a fixture mismatch:
the existing confined CLI `--json check` control returned exit 1 instead of 0.
Its process boundary rejected the real resolver's new native Keychain lookup.
The new missing-credential CLI/MCP tests instead launched unconfined children.
A scratch HOME and a fictional `HASNA_STATION` do not isolate macOS Keychain;
the station only selects the account passed to `/usr/bin/security`.

This repair changes tests and test helpers only. Production Darwin tool pinning,
the published contracts credential resolver, CLI formatting, MCP startup and
stdio initialization remain real. The related existing CLI list-refusal and
four MCP help/version tests use the same boundary.

## Boundaries and controls

- Children use canonical, owned, mode-0700 temporary homes. Startup cases receive
  a fresh environment and run with that home as cwd, avoiding inherited provider
  keys, configuration selectors, preload settings and project `.env` files.
- The native boundary accepts only the exact `security find-generic-password`
  argument vector for the fictional account and Recordings `api-key`/`api-url`
  service names. Status 44 models an absent item. Status 36 models denied
  interaction and must remain terminal even with an environment key available.
  No native Keychain command executes. Trace files contain service names and
  fixture outcomes only.
- The MCP preload validates the actual source entry and exact allowed arguments.
  It does not import the entry indirectly, replace `main()`, mock the resolver,
  or manufacture an initialize response. The real MCP SDK answers initialize.
  Listener attempts, denied operations, and the platform are separately recorded;
  startup refusals require exit 1, no response, zero listener attempts, and no
  database anywhere under the owned home.
- Local MCP startup still exercises the real maintenance-lease code. Only
  `/bin/ps -o lstart= -p <own child PID>` receives a fictional stable process-start
  string; it cannot enumerate or address another process. Local mode is tested
  with the fixture Keychain configured to deny access, and must perform zero
  Keychain lookups. Help/version likewise must resolve no credential and start
  no lease or listener.
- Fourteen negative MCP probes cover all Node child-process entry points, Bun
  spawn APIs, altered Keychain arguments, writes, fetch/preconnect, and listener
  startup. The existing CLI/trigger process-denial controls remain in place.
  Trigger dependency availability is fictional, so installed `rec` is not an
  input to a trigger/credential exit-code assertion.
- The existing per-child Darwin signing-fixture sandbox independently denies
  network access, host apps/Keychain/preferences/TCC reads, writes outside the
  owned home, and signals to outside processes. Its executable allowlist refuses
  real `security`, `defaults`, `open`, `codesign`, and `tccutil`; safe `--help`
  negative controls require the actual OS denial. A separate positive owned
  write, denied outside write and denied outside signal-0 control verifies the
  sandbox without inspecting owner data or signaling an application.
- Startup subprocesses have a 15-second deadline and 64 KiB per output stream.
  A hung child and excessive output are explicit test errors. The supervisor
  kills only its still-live owned process group, clears its timer and awaits exit.
  Trigger subprocesses also have a 15-second/64-KiB bound.

The fixtures retain actual Darwin behavior. The pre-existing explicit
unsupported-host trigger case remains separate. No Linux runtime validation is
claimed by this checkpoint. Do not add an outer sandbox around these tests:
macOS does not support nesting their child sandbox inside another sandbox.

## Focused validation

Run with Bun **1.3.14**, a fresh temporary HOME/TMPDIR, and an environment containing
only those paths, `PATH=/usr/bin:/bin`, and `NO_COLOR=1`. Invoke the pinned Bun by
absolute path from `apps/recordings`. The test parent creates each child's sandbox.

```sh
bun test --timeout 30000 src/__tests__/trigger-diagnosis.test.ts \
  src/__tests__/mcp-fail-closed.test.ts src/__tests__/mcp-binary-options.test.ts
bun test --timeout 30000 src/__tests__/cli.test.ts --test-name-pattern \
  'app fixture|app status|app permissions|duplicate installs|with nothing installed|app help advertises|app exposes|machine-readable dependency status|check with no credential|check preserves terminal|without hosted env'
bun scripts/ci-linux-suite.ts --check
bun scripts/release-suite-gate.ts --all --plan
```

Final Darwin results: **46 pass, 1 existing strace skip, 0 fail, 237 assertions**
for the first group; **15 pass, 0 fail, 136 assertions** for the selected CLI
cases. Package typecheck, strict typechecking of all four test files and their
helpers, and package build pass. Discovery reports **81 files, all gated**;
the new MCP suite appears exactly once in the ordinary group. The existing gate
therefore needs no manifest change or exception.

The task worktree reused the root and Recordings dependency trees. Its required
repository-wide attempts stopped on missing unrelated workspace dependencies:
the affected build could not resolve dependencies such as `zod` in other packages,
and `check:manifests` could not run the contracts CLI without `commander`.
These are not reported as passing; the integration worktree's full checks are
separate evidence. No broad release gate, package publication, live application,
microphone, clipboard, provider request, or owner credential/privacy operation was
run for this repair.
