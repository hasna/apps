# PostgreSQL port contract

The PostgreSQL migration is a schema and security contract for a later self-hosted adapter. PostgreSQL runtime support is not ready in this slice: there is no driver, transaction adapter, or controller-key persistence implementation, and SQLite/PostgreSQL runtime parity is not claimed. The migrations have a reproducible live PostgreSQL 16.13 integration proof: `bun run test:postgres-migrations`. It uses local peer authentication, task-scoped temporary databases, three passwordless test roles, and trap-based cleanup with an explicit zero-residue query. The proof's exact migration role is `${prefix}_migrator`, created as `LOGIN NOSUPERUSER NOINHERIT NOCREATEDB NOCREATEROLE NOREPLICATION BYPASSRLS`; every 0001, 0002, and 0003 migration command runs with `current_user` set to that role while every migrated table has forced RLS. `${prefix}_rejected_migrator` has the same attributes except `NOBYPASSRLS`, owns a forced-RLS test database, and proves 0002 fails at its first precondition without changing schema version, columns, data, or authority. `${prefix}_app` is the distinct `NOBYPASSRLS` application role used for isolation and concurrent-writer checks. The task-scoped prefix makes parallel proofs safe; a deployment may name the equivalent dedicated role `computers_migrator`.

PostgreSQL 0002 checks `current_user` in `pg_roles` before any lock or mutation and fails closed unless that executing role has `BYPASSRLS` or is a superuser. Superuser is accepted as PostgreSQL's technical equivalent, but the supported operational model is the dedicated, non-superuser `BYPASSRLS` role above. That role owns the database/schema objects so it can apply DDL; table ownership alone is not accepted as an RLS bypass. The application role must be separately created as `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`, must not own the schema or tables, and must receive only explicit DML and sequence grants plus `EXECUTE` on `computers_current_tenant()`. Public table/function access is revoked. The application must set `computers.tenant_id` with transaction-local scope before each tenant transaction and clear it by ending that transaction. Missing or empty state resolves to no tenant, so every forced RLS policy denies access.

0002 first serializes migrators with `schema_migrations`, then takes transaction-scoped `SHARE ROW EXCLUSIVE` locks in this global order: `computers`, `operations`, `operation_attempts`, `provider_bindings`, `operation_home_leases`, `home_leases`, `resident_bindings`, `resident_enrollments`, `resident_identities`, `resident_nonces`, `profiles`, and `profile_revisions`; an already-existing `provider_assurance` table is locked immediately afterward. These locks exclude application writes from capture through commit or rollback while preserving ordinary reads. The executable proof uses a controllable transaction gate to hold the migrator after all 13 first-application locks are granted, starts an insert through the exact `${prefix}_app` role, and observes that writer's ungranted `RowExclusiveLock` on `computers` with the exact blocking migrator PID and `application_name`. The writer remains blocked until the gate is released, resumes only after migration commit, and fails its legacy strict-`local_vm` insert on the new constraint, leaving state `1:1:0` for migration generation, demoted legacy Computer, and rejected racing Computer. A separate gated two-migrator proof establishes overlap and directly observes the second migration session's ungranted `ShareRowExclusiveLock` on `schema_migrations` blocked by the exact first migration session before release; the final state proves generation changed exactly once and legacy authority was removed.

Only while version 2 is absent, 0002 captures every preexisting `local_vm` Computer in a transaction-local table, including rows already labeled `unverified_vm`. That first application increments `policy_generation` exactly once, which fences every operation stored at the legacy generation; quarantines every nonterminal Computer; retains `deleted` and `deleting`; deletes legacy provider bindings, resident bindings, resident nonces, home leases, and operation-home leases; and revokes live resident enrollments and identities. A direct PostgreSQL replay after version 2 or 3 captures no Computers, so it preserves exact values and counts across the valid post-migration Computer, operation, attempt, home-lease, resident, assurance, and provider-binding graph. The proof also verifies rollback on an injected 0002 conflict after capture and on invalid pre-0003 provider-binding provenance. The 0003 transaction preserves valid bindings and rejects cross-Computer, cross-provider, and cross-operation/attempt provenance rather than deleting or rewriting it.

The runtime adapter must reject pooled connections that retain a tenant setting, must test cross-tenant reads and writes using the actual application role, and must never connect as the migrator, owner, superuser, or a role with `BYPASSRLS`. These guarantees are structural only until those live tests exist.

PostgreSQL controllers must provide a persistent external install-ticket signing-key provider. The migration intentionally has no `controller_keys` table and does not pretend SQLite file protection applies to PostgreSQL. Key retrieval, rotation, backup, and access audit belong to the deployment's secret-management boundary; plaintext key material must never be returned or logged.
