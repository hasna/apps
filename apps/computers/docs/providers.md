# Provider contract

Provider adapters implement typed create/start/stop/quarantine/delete/restore/reconcile methods plus readiness. Every call carries the durable operation and provider attempt, including a stable provider idempotency key, monotonic execution-owner generation, cancellation signal, and current-ownership assertion. Outcomes are exactly `success`, `definite_failure`, or `unknown`.

Local mutations additionally hold a package-owned, inode-checked advisory lock. Lima locks are keyed by tenant/Computer resource. Adoption uses one state-root physical-resource lock and the same state-root supervision key regardless of the currently supplied adoption, host, tenant, owner, Computer, or profile configuration. A drifted controller configuration therefore cannot select a second lock or helper journal before persisted identity validation. The DB token, generation, and unexpired lease are rechecked around external commands and local state writes. Before a detached mutator is spawned, its owner atomically records a private supervision journal; PID and PGID are published only after spawn. A synchronous spawn rejection removes the prepared journal only after matching its private command identity. A later lock owner treats a live process group as busy/unknown, treats a genuinely ambiguous prepared journal as manual-recovery-only, and may clear a fully published dead process only before reconciliation. Cancellation is best-effort while the owning worker is alive; it is not immediate crash cancellation. The runner bounds stdout and stderr under one aggregate budget and terminates the process group on timeout, cancellation, or excess output.

Package-owned recovery files (supervision journals, create phases, manifests, adoption claims, and generated Lima request state) use same-directory publication. Contents are written to a private no-follow exclusive file and synchronized before publication. On Darwin, regular recovery files use Apple `fcntl(F_FULLFSYNC)`; an unavailable symbol or nonzero result fails closed. On non-Darwin hosts they use `fsync`. Replacements use atomic rename followed by parent-directory synchronization. Exclusive creation uses a synchronized temporary inode, atomic hard-link publication, parent synchronization, temporary-link removal, and a second parent synchronization. State removal validates the private regular-file identity before unlink and synchronizes the parent afterward. Newly created controller directories are also synchronized through their parent. Any file, inode, ownership, mode, link-count, or synchronization failure stops the operation rather than claiming a lifecycle result. The boundary follows Apple's [`fsync(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html) write-order guidance and [`fcntl(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html) definition of `F_FULLFSYNC`.

Darwin directory descriptors use `fsync`, not `F_FULLFSYNC`: Apple documents the stronger command for flushing file data and metadata, but does not provide a general package-level guarantee that `F_FULLFSYNC` is accepted for directory descriptors. Directory `fsync` is the strongest bounded namespace-ordering barrier used here, and any error still fails closed. Consequently this is a write-order and filesystem crash-consistency boundary, not a claim that macOS provides the same physical-media guarantee for directory entries that `F_FULLFSYNC` provides for regular files, nor a promise that defective storage hardware cannot lose acknowledged writes. Network filesystems and storage stacks that do not honor these operations are unsupported. A power loss can leave an unpublished random temporary file or, at the exclusive-link boundary, two names for one synchronized inode. Both are fail-closed: the canonical state is not accepted until it is an owner-only regular file with one link, and an operator must investigate unexpected temporary/link state before retrying.

Ambiguous prepared-journal recovery is deliberately an operator procedure because no PID was durably published. Stop every Computers worker sharing the `stateRoot`; externally quarantine or stop the affected host/VM; inspect the owner-only `stateRoot/command-journals/<sha256(resourceKey)>.json` and record its `resourceKey`, `argvDigest`, and `phase`; then prove from the controller process table and authoritative provider state that no matching command can still run. If process absence cannot be proved, keep the journal and reboot the controller host while the target remains externally quarantined. After absence is certain, recompute the filename from the exact resource key (`printf %s '<resourceKey>' | shasum -a 256`), verify that the file is the same owner-only regular file and still has `phase:"prepared"`, remove only that file, restart one worker, and let the existing operation reconcile before permitting another mutation. Never remove a prepared journal while a matching child may exist.

Reconciliation never repeats create, start, or restore. A reclaimed restrictive local operation first observes authoritative state under the existing resource lock and execution-owner checks. Adopted stop and quarantine transition only from a less restrictive observed state; adopted delete releases only the exact active claim after a stopped/quarantined authoritative preflight, and a durable `releasing` claim retries only that same idempotent release. Lima stop, quarantine, and delete issue only the needed idempotent restrictive command and then re-observe. Equal or stronger restrictive state completes without another external mutation. The controller accepts lifecycle evidence only from the success result's own top-level `lifecycle` field under the closed per-operation matrix: notably, reclaimed stop may persist an observed quarantined state instead of weakening it to stopped. Invalid, incompatible, nested, or metadata lifecycle values are not terminal evidence and remain fail-closed. A journal-owned partial local-VM create may be cleaned up restrictively, but creation is not resumed. A deterministic but unmarked VM or disk is never deleted or adopted merely by name.

Create success atomically advances observed Computer state, provider binding, assurance evidence tied to operation/attempt/fence/generation, volumes, resident binding, and audit/outbox effects. Definite create failure releases child quota only after absence or cleanup is authoritatively proven. Unknown outcomes preserve identity and quota.

Start and restore require a current typed home-lease capability binding tenant, Computer, home, holder, fence, and expiry. Missing or stale capabilities fail before the provider call.

## `local_machine`

Confinement is `dedicated_machine`, never `strict_vm`. The resident shares the OS boundary, so `residentIndependentIsolation` is false. Adoption is admin-only and references a pre-registered inventory ID. The operation's tenant-bound profile must exactly match both controller inventory and the built-in adopted profile. A controller helper must authoritatively observe matching host/boot identity, dedicated ownership, protected controller authority, and running state. Every helper call binds adoption, tenant, Computer, owner, monotonic claim generation, and an unpredictable package-generated claim fence. The versioned durable claim additionally binds configured host ID, profile ID, profile generation, built-in profile revision digest, and resolved profile digest. The versioned Computer manifest repeats the physical host and fenced claim identity. Active, releasing, and released claim reuse validates the exact claim/manifest/configuration tuple before observation, transition, release, or re-adoption; only the Computer ID may change after an exactly matching released claim advances to a new generation and fence. Stale release or transition results cannot alter a newer claim. A current resident heartbeat is required only for `residentBindingVerified:true` and resident authority; adoption remains successful without it and withholds the binding. Lifecycle transitions observe first and re-observe after a required mutation; metadata is never a power-state oracle. Release observes the exact active claim before durably entering `releasing`, then only that fenced claim may be retried. One exclusive host claim prevents double binding, while reconcile repairs the claim/manifest crash boundary.

Adoption claim schema version 2 and the manifest's versioned adoption identity are fail-closed. Pre-version-2 claims and manifests without the host identity are not auto-migrated because the missing profile/host binding cannot be reconstructed as authoritative evidence. Keep the host externally quarantined, verify inventory and physical identity out of band, and perform an operator-controlled retirement/re-adoption rather than editing legacy state in place.

## `local_vm`

The concrete backend is stock Lima **2.1.1 only**, with explicit `vmType=vz` and native `aarch64` on Apple Silicon macOS. It invokes absolute executables with typed argv, bounded environment and aggregate output, deterministic instance/disk names, and one raw retained per-Computer disk. List and disk output is parsed as bounded JSON Lines; empty successful instance output alone proves absence. Submitted YAML is not proof: the adapter reads the authoritative instance `lima.yaml` from that Computer's exact `LIMA_HOME`, rejects unknown top-level and nested fields, and accepts only the package-rendered subset. Per-Computer `_config/default.yaml`, `override.yaml`, and `base.yaml` are rejected rather than merged. This closes behavior from `copyToHost`, static forwards, `vmOpts`/VZ Rosetta, nested virtualization, firmware, user, DNS, CA certificates, upgrades, audio/video, mounts, provisioning, probes, networks, environment, proxy/resolver, containerd, Rosetta, SSH, and integrations outside the supported subset.

The retained disk is separately re-observed with exact name, raw format, requested byte size, canonical controller directory, ownership/mode, and exact non-empty instance plus instance-directory attachment whenever the VM exists. Every later lifecycle and reconciliation compares profile ID, generation, revision digest, and resolved digest to the current configured profile. Any mismatch prevents success. A nonzero mutating command is never terminal evidence by itself: authoritative post-observation must prove the final state, otherwise the outcome remains unknown and quota/ownership stay held.

Lima plain mode is necessary but insufficient: controller SSH/base keys still exist and default user networking can reach host services even with `hostResolver=false`. Every create, start, and reconcile result therefore remains `unverified_vm`, `externalEgressEnforced:false`, `residentIndependentIsolation:false`, and `residentBindingVerified:false`. Lima 2.1.1 resolves the host `ssh` executable through `PATH` and invokes `ssh-keygen` by name when creating its controller key. Because Bun replaces rather than extends a supplied environment, every `limactl` subprocess receives exactly `LIMA_HOME` plus `PATH=/usr/bin:/bin:/usr/sbin:/sbin`. That bounded system path keeps required macOS utilities available while excluding Homebrew (`/opt/homebrew`), MacPorts (`/opt/local`), Nix, and `/usr/local` tools.

Lima 2.1.1 validates but does not apply `limactl disk create --format`; when `qemu-img` is discoverable it creates qcow2. Computers therefore omits that ineffective flag. The same bounded path prevents Lima disk creation from finding those third-party QEMU installations, so its native image implementation creates a sparse raw file. Computers then authoritatively requires the retained disk to report exact raw format and size. `additionalDisks.format:false` prevents guest formatting; the disk is not claimed formatted, mounted, or usable durable home. No external Boolean verifier/bootstrap output can change assurance. socket_vmnet is rejected because it adds privileged host paths/sudoers surface.

Official design sources (retrieved 2026-07-15): [config](https://lima-vm.io/docs/config/), [create flags](https://lima-vm.io/docs/reference/limactl_create/), [plain mode](https://lima-vm.io/docs/config/plain/), [mounts](https://lima-vm.io/docs/config/mount/), [VZ](https://lima-vm.io/docs/config/vmtype/vz/), [user networking](https://lima-vm.io/docs/config/network/user/), [network modes](https://lima-vm.io/docs/config/network/), and Lima 2.1.1 source for [SSH executable lookup and controller key generation](https://github.com/lima-vm/lima/blob/v2.1.1/pkg/sshutil/sshutil.go), [disk creation](https://github.com/lima-vm/lima/blob/v2.1.1/cmd/limactl/disk.go), [QEMU/native selection](https://github.com/lima-vm/lima/blob/v2.1.1/pkg/imgutil/proxyimgutil/proxyimgutil.go), [QEMU qcow2 default](https://github.com/lima-vm/lima/blob/v2.1.1/pkg/qemuimgutil/qemuimgutil.go), and [native raw creation](https://github.com/lima-vm/lima/blob/v2.1.1/pkg/imgutil/nativeimgutil/nativeimgutil.go).

## Controller configuration

`COMPUTERS_LOCAL_CONFIG` points to a private (`0600`) JSON file. `stateRoot` and `limaHome` are controller-owned private directories. `limactlPath` and the adoption controller helper must be absolute, root/controller-owned executables without group/other write permission. Requests carry only `adoptionId` and `profileId`. The VM object accepts only `limactlPath`, `limaHome`, and `profile`; stale verifier/bootstrap fields are rejected.

```json
{
  "version": 1,
  "stateRoot": "/var/lib/computers/local",
  "vm": {
    "limactlPath": "/opt/homebrew/bin/limactl",
    "limaHome": "/var/lib/computers/local/lima",
    "profile": {
      "id": "profile_lima_arm64",
      "cpus": 4,
      "memoryGiB": 8,
      "rootDiskGiB": 32,
      "homeDiskGiB": 128,
      "imageLocation": "https://images.example.invalid/pinned-linux.img",
      "imageDigest": "sha256:REPLACE_WITH_64_LOWERCASE_HEX"
    }
  }
}
```

The example contains no credential. The image digest placeholder must be replaced before use. The profile image is required for `local_vm`; adopted `local_machine` profiles must omit image fields. `loadDotSSHPubKeys:false` disables loading public keys from the user's `~/.ssh`, but it does not disable Lima's controller-owned SSH identity.

## `aws_ec2`

The initial class is `unverified_vm`. Strict mode requires private subnets, no public IP/listener, IMDS IPv4/IPv6 disabled before the agent starts, no instance profile or guest credential chain, encrypted replaceable root and separately durable home, externally controlled egress, TTL/orphan/budget/tag reconciliation, and exact resident/image provenance. Temporary SSM profiles are limited to externally initiated, named-human, quarantined, expiring, audited break-glass with agent fencing and automatic detachment.

No provider credentials enter a Computer guest. EC2 remains unconfigured.
