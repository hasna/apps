# Architecture

Computers separates controller mode from provider kind. The included local controller uses SQLite; a future self-hosted controller uses the PostgreSQL schema and RLS policy. Provider ports are `local_machine`, `local_vm`, and `aws_ec2`.

Every public mutation enters `ComputersService`, passes `AuthorizationEngine`, and then uses `StoragePort`. The authorization decision combines tenant, principal, scope, bound Computer, owner, and policy generation. REST, SDK, CLI, and MCP do not implement independent policy shortcuts.

SQLite enables foreign keys, WAL, full synchronous writes, a busy timeout, parameterized queries, immediate transactions for allocation/idempotency, unique active owner assignment, durable controller-owned creation grants, atomic child quota reservation, one-time enrollment, replay nonces, one-writer home leases, immutable policy revisions, single-use tickets, append-only audit, and outbox records. A lifecycle request checks for an existing same-key operation before validating mutable Computer state. New lifecycle state validation and insertion share one immediate transaction; a start operation additionally requires and binds its current home-lease capability in that transaction, so workers cannot observe a performable start without the capability. Schema-v3 readiness verifies exact critical table and trigger DDL where the full definition is available, verifies column, index-order, and composite-FK structure through SQLite introspection, runs `foreign_key_check`, checks provider-binding provenance and row preservation across migration, and executes rollback-only negative probes for forbidden stock `local_vm` strict rows, negative execution-owner generations, and cross-Computer/provider/operation/attempt bindings. Every tenant-scoped lookup includes `tenant_id`.

Creation limits live only in `computer_create_grants`; child requests reference a grant but cannot choose a limit. The transaction validates grant tenant, parent, principal/owner, provider, active state, expiry, and current reservation count before inserting the Computer and reservation. Duplicate and distinct requests share the same immediate transaction and uniqueness constraints.

Persistent SQLite controllers generate the install-ticket HMAC key once in protected controller storage and force the database file to mode `0600`. In-memory or non-persistent storage must supply an explicit signing-key provider. Policy revision advancement atomically increments fences on older pending/running operations, and both the worker and resident reject an operation whose stored generation no longer matches the Computer.

PostgreSQL defines the same core resource families and stronger structural constraints, but runtime parity is deliberately not claimed. The package has no PostgreSQL adapter. Its migrations bind both assurance and provider bindings to the same Computer/provider, operation/Computer, and attempt/operation chain. PostgreSQL 0002 fails closed unless `current_user` is the documented dedicated `BYPASSRLS` migrator (or a superuser accepted as PostgreSQL's technical equivalent), serializes on the migration ledger, and locks every affected Computer, operation/attempt, provider-authority, home, resident, and profile table in one transaction-scoped order before capture. Only while version 2 is absent, it captures every preexisting `local_vm`, including already-unverified rows, increments each Computer generation exactly once, quarantines nonterminal states, preserves `deleted`/`deleting`, and revokes legacy provider binding, home, enrollment, identity, binding, and nonce authority. SQLite 0002 uses the same complete first-application capture within the migration runner's immediate transaction; v2/v3 replay is skipped from the ledger and preserves exact post-migration authority. The live local `test:postgres-migrations` proof executes 0001→0002→0003 under the exact forced-RLS migration role, rejects a `NOBYPASSRLS` owner before mutation, observes a concurrent application writer's exact awaited `computers` relation and blocking migrator through commit before the new constraint rejects it, observes one exact migration session waiting on the `schema_migrations` lock held by the other before proving exact-once authority state, preserves post-migration replay values, and verifies rollback and zero residue. See [the PostgreSQL contract](postgresql.md).

Durable operations are accepted before provider execution. The worker persists a provider attempt, provider idempotency key, resource identity, typed outcome, and provider binding. On provider success, storage recognizes only an own top-level `result.lifecycle` from the closed running/stopped/quarantined/deleted set and validates it against the operation before terminalization. Start and restore require running, stop permits stopped or the stronger quarantined observation, quarantine requires quarantined, delete requires deleted, and create must match its explicit desired state. A valid stronger stop observation atomically completes the operation/attempt and audit/outbox while retaining the Computer as quarantined; unrecognized or incompatible values cannot terminalize the operation or drive Computer state. Nested metadata is not lifecycle evidence. `unknown` outcomes hold child quota and are sent to the adapter's reconciliation method until the resource is adopted or definitely absent/cleaned. The included adapters are unconfigured, so real provider execution still fails truthfully with `provider_not_configured`.
