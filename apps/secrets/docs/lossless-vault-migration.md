# Lossless vault migration protocol

`secrets migrate-vault` transfers one complete supported vault through the configured account API. It does not call generic export/import and never deletes source data. This protocol must be deployed with migration `secrets_0014_lossless_vault_migrations` before use. A healthy older API is not sufficient.

Required options are `--source <absolute SQLite path>`, `--key-file <existing key path>`, stable UUIDs `--source-id` and `--migration-id`, and the explicitly expected destination `--tenant <uuid>`. For an existing KMS-wrapped key file, also supply `--kms-key-id <reference>` and `--kms-region <region>`. Only KMS Decrypt is used through the SDK's existing credential chain; no key is generated, rewrapped, written to a temporary file or deleted. Local key files must contain an existing 32-byte hexadecimal key and deny group/other access. Do not pass key material on the command line.

The CLI uses the normal shared resolver to validate one authority/credential pair, including pointer completion, before dispatching the capability request. It binds subsequent requests to that first pair and refuses any credential or authority change before further network I/O and checks the authenticated `GET /v1/migrations/vault` capability and destination tenant before opening the database or key. POST additionally binds the expected tenant and key ID in headers and body, checked before body parsing or persistence, so credential changes cannot retarget the import. The dedicated `secrets:migrate` scope (or an applicable wildcard) is required; ordinary read/write keys cannot invoke migration. Remote transport requires HTTPS; loopback HTTP is permitted for isolated fixtures. Request bodies contain decrypted values only in process memory and protected transport, never exported files or log output. JavaScript strings cannot guarantee physical memory zeroization; key byte buffers are cleared after use. Do not enable request-body capture in surrounding infrastructure.

The read-only snapshot covers `secrets`, `vault_items`, `audit_log`, `users`, `feedback`, and `secret_versions`. It preserves every supported row and original identity, timestamp, structured payload and history entry. Unknown/missing tables or columns, unreadable values, duplicate identities and snapshots over 100,000 rows or 16 MiB are rejected. Legacy schema adapters and larger chunked transfers require separate implementation; no rows are silently omitted. Reads use a consistent SQLite transaction and do not invoke local schema migrations. Existing WAL sidecar/locking behavior is SQLite-owned; keep the application quiescent and preserve the entire source vault directory until acceptance.

`POST /v1/migrations/vault` locks the active tenant/API-key authority and destination tables inside one PostgreSQL transaction. Before authority, journal or payload reads and writes, the import transaction forces synchronous commit and requires PostgreSQL fsync and full-page writes to be enabled. Unsafe settings return `migration_durability_unavailable` without importing records; transaction-local settings restore the caller session on success or rollback. Global identity collisions, including another tenant's keys, cause a generic conflict without disclosing existing data. There is no overwrite mode. Original audit IDs and the source audit sequence high-water mark are retained; the destination sequence is advanced safely. Imported history keys are excluded from ordinary automatic retention pruning. Later explicit user edits/deletions are still intentional operations, so a repeated verification can report drift.

Current values, structured data and historical values are encrypted under the server master key. Historical fingerprints must be regenerated under that key; the original fingerprint and complete source metadata remain in an encrypted provenance manifest. Verification decrypts and compares the actual inserted rows against that manifest, including all supported fields, and returns a fresh nonce-keyed HMAC proof. The CLI checks that proof and rereads the source snapshot to detect concurrent changes. It prints only identities/counts and verified status; it never prints proof material or a manifest.

Retry an interrupted transfer with exactly the same source ID, migration ID and unchanged source. The durable receipt makes a committed retry replay-safe and checks current destination rows; a different payload under that ID is rejected. A transport error may occur after commit: keep the source and retry rather than inventing a new ID or assuming nothing happened. Atomic bounded transfer is resumable by whole-request replay, not by chunk upload. A source that changed requires explicit reconciliation; no automatic merge is attempted.

Migration success is not source retirement authorization. All dependent clients, credential consumers and historical access paths must pass account-backed acceptance first. Keep backups and existing key material. The receipt always says `deletion_authorized: false`.

The service role must be non-superuser and non-BYPASSRLS. Eight data/provenance tables enforce FORCE ROW LEVEL SECURITY using transaction-local tenant context. Every ordinary API store operation runs atomically in that context after rechecking active tenant/key/scopes. The history table gains explicit tenant ownership; existing histories with no attributable current secret remain unassigned and invisible until separately reconciled. A protected key-ownership trigger prevents another tenant from claiming orphaned or deleted global key identities. Its SECURITY DEFINER function pins the migration schema and places pg_temp last; the service role must not have direct DML access to secret_key_owners. Grant only the needed data-table DML, authority reads and audit-sequence privileges. Startup and readiness fail closed for a bypass role or missing RLS schema; baseline-history maintenance iterates active tenants under the same boundary. This changes the schema/runtime security contract and requires an independently reviewed migration and service-role rollout, not just an image replacement.

Validation uses synthetic SQLite, injected KMS decryption and an isolated PostgreSQL schema. Run the migration integration fixture only with a disposable `SECRETS_TEST_DATABASE_URL`; no live vault is part of these tests. This change is separate from PR #1891's ordinary command routing/maintenance work.
