# Atomic project migration protocol v1

`GET /v1/project-migrations` advertises a bounded, server-owned migration capability. Both GET and POST require the explicit `todos:migrate` scope in addition to their ordinary read/write scope; a wildcard-only or ordinary write key is insufficient. The server must have a stable, operator-provisioned UUID in `HASNA_TODOS_MIGRATION_DEPLOYMENT_ID`. It must identify this database deployment across restarts and must not be copied to another deployment. No setting or migration is activated by this source change.

Clients must freeze the capability's deployment UUID, tenant and authenticated key ID, their API origin, and credential for the entire operation. POST supplies that expected authority, schema version 1, a reusable operation ID, snapshot, and SHA-256 of canonical JSON (object keys sorted; array order retained; finite JSON only). The server compares authority to its configured deployment and authenticated principal before any record writes. SDK methods expose capability and submission, but do not automatically migrate a client database.

The operation accepts projects, tasks, plans, taskLists and immutable auditHistory, plus project tombstones retaining their original payload. Other nonempty snapshot families and non-project tombstones explicitly fail before writes. Snapshot input is limited to 1,000 unique identities, 2 MiB and depth 32; the destination project/task/plan/list/history scope is limited to 10,000 records, 16 MiB total payload bytes and 2 MiB per record, checked by database aggregate before payloads are fetched. This is not a complete database import: machines, templates, other relationship tables and project-machine path records require their separate protocols. Existing historical path records are retained untouched. The legacy `/v1/import` refusal for project tombstones is unchanged.

Record clocks compare canonical millisecond UTC `updated_at`, then same-record integer version (null means zero). Older input is preserved in the manifest with a superseded receipt; newer live destination records remain live. Identical rows replay. Divergent equal-clock records, including a live/deleted tie, conflict rather than choose a winner. Divergent duplicate identities and hierarchy cycles reject. Identical duplicates are represented once in per-identity receipts while the original manifest retains every occurrence. Deleted records are never implicitly resurrected.

An applicable newer project tombstone detaches linked tasks, plans, lists and child projects without deleting content. Task versions increment; detaches use the historical deletion clock rather than invent a current timestamp. Linked records with newer timestamps, or equal timestamps and higher versions, and active task leases block reconciliation. Task-plan project mismatches, unknown history tasks and unresolved task/plan list references also reject before writes; historical list routing can require explicit reconciliation. List-scope collisions roll back the operation. Existing history rows are immutable: a divergent same-ID history row rejects. The journal retains original source payloads and affected destination before-state, including the original relationship fields. Receipts contain hashes and outcomes, not message/task content. A record imported and then detached has two explicit receipt transitions.

The backend uses the existing graph advisory lock and a bounded table write lock to fence older writers too. This blocks writes across services sharing that table while the transaction executes; use a maintenance window for larger batches. The transaction explicitly enables synchronous commit and refuses PostgreSQL with fsync or full-page writes disabled before importing any record. The caller session setting is restored automatically at transaction end. Lock timeout is 5 seconds, statement timeout 15 seconds, with a 20-second checked write-loop budget. Source rows, detaches, history and immutable receipt/manifest commit in one transaction. Any error rolls back all changes. No automatic schema migration is performed inside the transaction; the existing record schema is ensured first.

After an interrupted or ambiguous response, repeat the same operation ID, authority and request. The journal returns the original terminal receipt without reapplying changes. Reusing the ID with another request is a conflict. Do not generate a new ID to hide uncertainty. A complete receipt means this bounded operation committed, not that every SQLite table was migrated or that local files may be deleted. Operators must reconcile unsupported records and verify full migration separately. Journals have no ordinary list/export route, and no manifest payload is logged.
