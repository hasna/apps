# FINAL PLAN — hasna/workflows (candidate alias hasna/graphs)

A public OSS member of hasna/apps: package `@hasna/workflows`, four surfaces per monorepo law (CLI bin, MCP bin, `-serve` server bin, `./sdk` module). It speaks ONE universal graph workflow language (nodes with prompts/output-schemas, edges with dependencies), owns its execution through a daemon + worker model on designated machines, stores everything under `~/.hasna/workflows/`, and works with the major coding agents through their SDKs/protocols — never by spawning them headless, never by minting or depending on any harness workflow format (Claude Code's Workflow-tool JS is deliberately unused). PLAN ONLY — nothing executed.

## 1. Verdict on the judge's draft

Adopt the judge's verdict (capability-graded hybrid, daemon-owns-durability) with four concrete corrections from final review:

1. **SQLite is not a shared network store.** The draft's "remote runs = daemon on each designated station registering against the shared store" is false under SQLite (single-writer, local file; NFS-style sharing is a footgun). The honest mapping, which matches the owner's own words: **SQLite = single-station/local backend (phase 1, user-hosted single box); PostgreSQL = the shared store that makes multi-station remote real (phase 2+).** A daemon on SQLite must refuse multi-daemon registration against the same file; multi-daemon mode requires `HASNA_WORKFLOWS_DATABASE_URL` (PG). Litestream gives SQLite DR (read-replicas at best), never multi-writer.
2. **The kai lane cannot live inside the public package as drafted.** hasna/apps law forbids `@hasna-internal/*` dependencies in the public tree (CI dep-direction + name-conformance gates). Measured: `@hasna-internal/kai` 0.1.1-rc.2 is a CLI-only package (bin `dsh`, no exports); `@hasna-internal/kai-base` 0.1.1-rc.2 is published with exports; but kai-headless/kai-app-boot/kai-cordis-client-runner/kai-sdk/kai-core all 404 on the public registry despite being listed as dependencies of the root package. Resolution: the kai adapter ships as a **private companion package** (e.g. `@hasna-internal/kai-workflows-adapter`) that registers into the workflows adapter registry at runtime via a plugin seam; the public tarball never references it. Phase-0 gate: inventory exactly which `@hasna-internal/kai-*` packages are published and from which registry (public vs private).
3. **The opencode2 pin must name the artifact source.** Measured: installed `opencode2` is v0.0.0-beta-18155 while npm latest `@opencode-ai/cli` is 0.0.0-beta-17823 — the local build is NEWER than the published one. "Pinned beta" is ambiguous; the lane registry pins the exact artifact (package version or local build hash) and the phase-2 gate verifies the operation-ID set against that exact artifact (the measured 401-on-guessed-operations stands).
4. **The `event:<webhook>` trigger duplicates hasna/events.** hasna/events owns webhook delivery (outbox + emission + TLS verification). Workflows mints no webhook listener: trigger vocabulary is `manual | loop:<name> | factory | events:<event-name>`, and the events app calls workflows' authenticated trigger endpoint like loops and factory do.

All other draft SDK claims verified live (2026-08-25): `@anthropic-ai/claude-agent-sdk` 0.3.245 (importable, exports present) — pin 0.3.x correct; `@openai/codex-sdk` 0.149.1 (importable, version-synced with the CLI it spawns) — pin 0.149.x correct; `@cursor/sdk` 1.0.28 (importable; native sqlite3 binding lives in the platform optionalDeps packages) — pin and gates correct; `@opencode-ai/sdk` 1.18.23 with `./v2` subpath export — correct; `@hasna/codewith` 0.1.95 has NO exports field (judge's decisive fact #1 confirmed) and `codewith app-server generate-ts`, `agent start --idempotency-key`, `agent logs/attach/stop`, `exec-server` all exist in the installed binary (measured). The adjudication that vendor-protocol-generated bindings and first-party scriptable client protocols count as "their SDK" is necessary: a package-only reading makes the owner's own list unsatisfiable.

## 2. The universal graph language

YAML definition files, git-trackable, diffable, reviewable, validated at parse time (`workflows validate` rejects unknown input references, cycles, non-deterministic shapes before deployment).

Per node: `id` (stable kebab-case), `lane` (claude | codex | codewith | opencode | kai | cursor), `prompt` (template over `{{inputs.<node>.<field>}}` and `{{run.*}}`), `outputSchema` (JSON Schema; enforced natively where the lane supports structured output — Claude `outputFormat json_schema`, Codex `output_schema` — and daemon-side against the same schema where it does not, so graph semantics are identical), `model`/`effort` (config-driven routing table; gpt-5.3-codex-spark excluded by the fleet ruling, enforced in the routing table), `retry` (attempts, backoff), `budget` (maxBudgetUsd/maxTurns), `timeout`, `machine` (tag or name; `any` default), `env`/`secrets` (vault/accounts REFERENCES only — key names, never values; resolved at the dispatch boundary), `for_each` (fan-out over a prior node's output array), `wait_for_event` (pause), `sleep`, `on_error` (an error-handling node reachable from failing nodes).

Edges: explicit `needs` list; fan-out implicit (multiple dependents run in parallel); fan-in implicit (a node runs when all needs inputs are present); conditional edges (BPMN XOR semantics) via `when:` on an edge plus `default` — conditions live on edges, not nodes. Entry via `trigger`. No while-loop in v1: `for_each` + `wait_for_event` + `retry`/`on_error` covers the loop class; add `while` only on a real second instance (elegance: smallest set that does the job).

Versioning: `version:` on definitions; a run binds to the exact definition content hash at start (run = definitionHash + inputs + idempotency_key). Runs are immutable once started.

## 3. Daemon + workers

One daemon process per station (product-owned, per the fleet daemon-worker taxonomy: control/execution/observation planes, leases, fencing, terminal receipts). Daemon owns: graph state machine, claim/dispatch loop, machine registry, trigger API (authenticated), reaper (any-daemon-can-reap, DB-timestamp-coordinated; leaderless).

Workers: a pool per station sized by MEASURED per-station RAM ceilings (the ~1 GiB/agent floor is doc-only — measure on fleet stations; this is the parallelism ceiling and a machine property). One agent SDK session = one subprocess (Claude: one `query()` = one claude subprocess; codex: one thread = one spawned CLI process). Claims: SQLite `UPDATE ... RETURNING` state-gated with lease expiry + claim token (Intent Bus pattern; SQLite has no SKIP LOCKED) vs Postgres `FOR UPDATE SKIP LOCKED` in short transactions (commit dequeue, do work, commit completion) behind ONE claim function. Leases carry fence generations; results from an older worker after lease expiry/takeover are rejected.

Machine registry (Nomad-lite): daemons heartbeat every ~10–30s with (machine, workload, running node lease ids); TTL down-detection; `initializing` after reconnect until allocation view reconciled; GC of dead registrations; node→machine binding by `machine:` tag. Registration is authenticated with a per-station install token (machine-kind runner token precedent) so a rogue process cannot register as a station and receive work. Remote runs = install the daemon on each designated station (registers via heartbeat against the shared store — PostgreSQL in multi-daemon mode); no central ssh-exec of agents.

Async by construction: a node claim is enqueued, a worker picks it up, typed events stream back, the node completes; the daemon never blocks on an agent. Alive triad: heartbeat + lease + reaper; run records and receipts per the taxonomy (durable-effect-before-acknowledgement).

## 4. Executor registry (adapters)

One `NodeExecutor` interface behind the daemon: `run(node, input, sessionRef) → typed event stream`; `resume`; `interrupt`; `pullState`. Adapters translate node→agent-call and agent-events→node-events ONLY — never durability, state, or scheduling (no mini-SDKs inside adapters; that state layer exists exactly once, in the daemon's store). Adapter kind is assigned by the checkable maturity rule: (a) first-party maintained package, (b) documented typed events + resume + streaming, (c) machine-bound mode exists, (d) pinned version recorded in the registry. A lane is wired only when all four verify on the installed version; unwired lanes show in `workflows lanes` as not-ready with the reason; `workflows lanes probe <lane>` re-runs the four checks live (the capability-pin expiry lesson: re-probe, never assume).

- **claude** → `@anthropic-ai/claude-agent-sdk` (TS, pinned 0.3.x, currently 0.3.245) — FULL SDK lane. Node = one `query()` session (fresh or resumed) with per-node `env`, `outputFormat: json_schema`, `maxBudgetUsd`, `settingSources: []` isolation, per-run cwd inside the run workspace, hooks (PreToolUse/PostToolUse) as the audit surface feeding typed node events, and OUR SessionStore adapter mirroring the transcript into `~/.hasna/workflows/sessions/<run>/agent/` (verified: official S3/Redis/Postgres store adapters exist; SessionKey carries subpath so subagent transcripts mirror too). In-session subagents may refine a node but are not the execution fabric (depth-3/concurrency-20 caps).
- **codex** → `@openai/codex-sdk` (TS, pinned 0.149.x, currently 0.149.1) — FULL SDK lane. thread_start/thread_resume + turn run/steer/interrupt; `output_schema`; model/effort per turn; sandbox preset default `workspace_write` (never `full_access`); spark excluded.
- **kai** → in-process `@hasna-internal/kai-*` SDK — FULL SDK lane, but shipped as a PRIVATE COMPANION adapter package (see verdict correction #2) because hasna/apps may not depend on `@hasna-internal/*`. Gates: publish-completeness inventory of the kai packages; placement ruling; prove headless in-process drive without booting the web front door. We own the fork, so gaps are extendable by us.
- **codewith** → harness-protocol lane via `codewith app-server generate-ts` bindings (the vendor's own sanctioned programmatic surface; `@hasna/codewith` pinned 0.1.95, no exports field — adjudicated as "their SDK"). Durable background agents via `agent start --idempotency-key` (retry-safe spawn, verified in the installed binary), `agent logs`/`attach` for events, `exec-server --remote` for machine designation. This adapter is the template for thin-protocol lanes and is in-house-extendable.
- **opencode** → DEFERRED (phase 2): pinned `opencode2` beta + generated `@opencode-ai/sdk/v2` client (subpath export verified on 1.18.23); the measured 401 on guessed operation IDs means the operation-ID set must be verified against the pinned artifact before wiring; upgrade to stable v2 SDK when it exists.
- **cursor** → `@cursor/sdk` (pinned 1.0.28), LOCAL (in-process) mode ONLY — machine-bound, satisfies "machines you designate". Cloud mode rejected (Cursor's VMs). Gates: local-mode getRun/resume across daemon restart verified; sqlite3 advisory on the platform package's native binding verified or pinned to a fixed version.
- **Fallback rule**: a protocol gap marks the lane not-ready and routes to the owning package (fix-once). Bare exec/headless one-shot is NEVER the fallback for a gap.

## 5. Storage

Owner-mandated layout: `~/.hasna/workflows/` containing `workflows/` (YAML definitions) and `sessions/`; plus `workflows.db` (SQLite, WAL + busy_timeout) or PostgreSQL via `HASNA_WORKFLOWS_DATABASE_URL`. One schema for both backends; one claim function behind two dialects; the fleet two-backend recipe applies (client transport + HTTP store when hosted; `-serve` is the server, fail-closed URL-without-key).

`sessions/<run-id>/`: `events.jsonl` (append-only WAL — the source of truth), `snapshot.json` (bounded derived state: snapshot at node completion, compact on a size threshold — bounded by rule, not aspiration), `nodes/<node-id>.json` (per-node memoized output + result receipt), `agent/` (agent transcript mirror: Claude JSONL via our SessionStore adapter, codex thread export, etc.).

Live session persistence (owner's "saved as agents write / pulled instantly mid-async-run"): WAL-before-execute (event appended BEFORE the side effect it records); write-as-you-go (adapters forward agent events as they stream; daemon appends continuously); torn-run repair (crash mid-turn closes the orphaned turn with a synthetic `interrupted` end — never truncate, DeepSeek harness pattern); bounded snapshot + live-load rule (a live `load(runId)` waits until the in-memory snapshot is durable); resume = per-node memoized outputs + replay (completed nodes return stored outputs without re-executing) with agent reasoning state checkpointed per session (non-deterministic, so checkpoint not replay) and a config-identity hash guard on resume (Reactive Agents DurableConfigMismatchError precedent).

Core tables (the 3-table state machine): `workflows` (definition_hash, status, idempotency_key, trigger, machine, tenant_id), `nodes` (status, input, output JSON, attempts, lease, machine, fence generation, tenant_id), `events` (append-only per-run history, tenant_id); plus `daemons` (heartbeat registry) and `leases`. Hosted (Postgres) mode is multi-tenant: tenant_id on all rows + RLS (fleet db-migration-rls skill), per-tenant API keys. SQLite mode is single-tenant.

## 6. CLI surface

`workflows init` | `workflows validate <file>` | `workflows run <file|name> [--input k=v] [--machine <tag>]` | `workflows runs list|show <id>|events <id>|cancel <id>` | `workflows nodes show <run-id> <node-id>` | `workflows sessions pull <run-id>` | `workflows daemon start|stop|status` | `workflows machines list|status` | `workflows lanes list|probe <lane>` | `workflows resume <run-id> [--from <node-id>]` | `workflows graph <file>` | `workflows serve` (/v1 API + authenticated trigger endpoints that loops/factory/events call).

## 7. Security

- Credentials: values never in definitions, stores, events, node outputs, or transcripts. Per-node `env`/`secrets` carry vault/accounts key names only; the daemon resolves at the dispatch boundary and delivers via secrets-exec-style injection into the spawned agent subprocess env (Claude per-query `env` — measured: TS env replaces subprocess env; codex per-turn env).
- **Write-gate on outputs** (new, closes a real gap): node outputs and app-authored events pass a secrets-scan gate (secrets-scan-input-style) before persisting to `nodes/*.json` and `events.jsonl`; a finding fails the node with a redaction instruction. The agent transcript mirror is treated as the known fleet transcript surface (stored at rest; redaction backstop where it exists), never the channel for credentials.
- Sandboxing: per-node isolation via `settingSources: []` + per-tenant `CLAUDE_CONFIG_DIR` + per-run cwd inside the run workspace (the documented multi-tenant recipe); codex sandbox presets defaulted to `workspace_write`; hooks (canUseTool/PreToolUse) as the audit surface, streaming every tool call into typed node events.
- Trigger API and daemon registration authenticated: per-integration bearer keys (loops/factory/events), per-station install tokens for daemon heartbeat registration.
- At rest: SQLite inherits host disk; PG inherits RDS encryption; Litestream-to-encrypted-bucket is the phase-3 replication option.

## OWNER AMENDMENTS — 2026-08-25 (binding, supersede the sections above)

1. **While-loop IS in v1.** The plan's "No while-loop in v1" clause is overruled. The v1 graph language includes a `while` node: `while: {condition: <expression over inputs/run state>, maxIterations: <declared bound>, exitOnVerifiedState: true}` — the loop body is wired via edges from the while node; the loop re-executes the body while the condition holds; it terminates at `maxIterations` (exhaustion is a terminal failure with the evidence, never silent) or when the exit condition verifiably holds. Phase-1 scope includes the while node in `validate` and the daemon's loop-execution semantics.
2. **Live verification standard.** Verification is never just `bun test` + rc=0. An agent exercises EVERY CLI command live as a real user — real operations against the real store (init creates the store, validate accepts/rejects real graphs, run executes a real graph, runs list/show/events return real records, sessions pull returns real mid-run state, resume restores a real interrupted run) — and returns a per-command GO/NO_GO with evidence plus an overall GO/NO_GO.
3. **kai adapter plugin seam (phase-2).** The plan defines the seam the companion adapter registers into: adapter load path `~/.hasna/workflows/adapters/`, registration + version-pin mechanism (manifest entry naming package, version, lane), and a dependency gate guaranteeing the public tarball never references `@hasna-internal/*` (publish-guard extended to check packed `dependencies`/`optionalDependencies` for the private scope, not only infra strings).
4. **Command count convention.** The CLI surface is 14 verbs: init, validate, run, runs, nodes, sessions (pull), daemon, machines, lanes (probe), resume, graph, serve — "pull" and "probe" count as their own verbs. Coverage in the plan is complete.

5. **SDK integration scope — narrowed (owner 2026-08-25).** For starters the app integrates with exactly FOUR lanes: **codex** (`@openai/codex-sdk`), **claude code** (`@anthropic-ai/claude-agent-sdk` — our own harness), **cursor** (`@cursor/sdk`, local mode), and **grok** (xAI Grok SDK). codewith, opencode, and kai are NOT wired in v1/phase-1/phase-2 starters — they may appear in `workflows lanes` as not-ready with the reason. The executor registry, the phase-1/2 build scope, and the verification lanes all target this four-lane set. "Include our own harness" (owner 2026-08-25): the verification panel includes a lens that drives the claude lane through the Agent SDK (Claude Code = our harness) and executes a drain-shaped workflow (our standing-lane shape) end-to-end.

6. **grok lane definition — grok is a PROTOCOL lane, not an SDK lane (owner 2026-08-25, resolved by the plan-validation gate).** Measured 2026-08-25 against registry.npmjs.org: there is NO official xAI TypeScript SDK. `@xai[-]official/grok@1.0.5` is a CLI binary wrapper (main/exports/types all null); all plausible scoped SDK names 404; `grok-sdk` is the npm 0.0.1-security placeholder; `@ai-sdk/xai@4.0.44` is Vercel's third-party provider.
